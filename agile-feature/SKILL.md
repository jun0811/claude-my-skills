# 애자일 기능 개발 워크플로우

설계 → 구현 → 테스트 → 결과 4단계를 순서대로 진행하며, 각 단계 산출물을 현재 프로젝트의 `.claude/tasks/<기능명>/`에 문서로 남긴다. 각 단계는 사용자 승인을 받은 뒤에만 다음 단계로 진행한다 (자동 진행 금지). 이 스킬은 다른 플러그인 없이 단독으로 동작한다.

## 사용법

`/agile-feature <기능명>`

## 준비

1. **기능명 정규화**: 인자로 받은 기능명을 파일 시스템에 안전한 kebab-case로 정규화해 디렉터리명으로 쓴다. 공백은 `-`로, `/` `\` `..` 등 경로 문자는 제거한다. 원래 기능명은 각 문서 제목에 그대로 유지한다. (예: `/agile-feature 사용자 로그인 개선` → 디렉터리 `user-login-improvement/`, 문서 제목 "사용자 로그인 개선")
2. **기존 작업 확인**: `.claude/tasks/<기능명>/`이 이미 있으면 안의 문서를 확인한다. 마지막으로 완료된 단계와 다음 진행 단계를 사용자에게 알리고, 기존 문서를 임의로 덮어쓰지 않는다. 중단된 작업은 마지막 체크포인트부터 재개한다. 처음부터 다시 하려는 경우에만, 재설계 여부를 사용자에게 확인한 뒤 진행한다. 디렉터리가 없으면 생성한다.
3. 프로젝트 루트에 `CLAUDE.md`, `docs/ARCHITECTURE.md`, `docs/CONVENTIONS.md`, `docs/TESTING.md` 등이 있으면 읽어서 이후 단계에서 프로젝트 고유 규칙(네이밍, 아키텍처 패턴, 테스트 명령어 등)으로 반영한다. 없으면 일반적인 소프트웨어 엔지니어링 관례를 기본값으로 쓴다.
4. 이 스킬은 git commit을 직접 수행하지 않는다. 각 단계 완료 시 "커밋은 직접 진행해주세요"라고 안내만 한다.

## Phase 1 — 설계 (`01-design.md`)

먼저 관련 기존 코드와 프로젝트 문서를 조사한 뒤, 대화로 요구사항을 좁혀간다:
- 한 번에 질문 1개씩만 한다. 가능하면 멀티초이스로 물어서 답하기 쉽게 한다.
- 목적/제약조건/성공 기준을 파악하는 데 집중한다.
- 요구사항이 충분히 파악되면 2~3개의 구현 접근법을 장단점과 함께 제시하고, 추천안과 이유를 먼저 말한다.
- **승인 밀도는 기능 규모에 맞춘다.** 작은 기능은 핵심 질문 몇 개 후 전체 설계안을 한 번에 제시하고 승인받는다. 중간 이상 규모는 설계를 논리적으로 연결된 2~3개 묶음으로 나눠 제시하되, 되돌리기 어렵거나 구현 범위에 큰 영향을 주는 의사결정이 포함된 묶음마다 확인을 받는다. "매 문장 확인" 같은 과도한 승인은 피한다.
- YAGNI 원칙: 불필요한 기능/추상화는 설계에서 먼저 걷어낸다.

확정된 설계를 `.claude/tasks/<기능명>/01-design.md`에 저장한다. 포함 내용: 목적 / 요구사항(제외 범위 포함) / 제약조건 / **참고한 기존 코드·문서**(파일 경로와 참고 이유) / 검토한 접근법과 추천안 / 아키텍처 개요 / 데이터 흐름 / 에러 처리 방침.

**체크포인트**: "설계가 확정되었습니다. 구현 단계로 진행할까요?" — 승인 시에만 Phase 2로 진행.

## Phase 2 — 구현 (`02-implementation.md`)

`01-design.md`를 다시 읽고, 다음 기준으로 단계별 구현 계획을 세운다:
- 각 단계는 독립적으로 검증 가능한 단위로 쪼갠다 (파일/함수 단위).
- 각 단계마다 "무엇을 바꾸는지"와 "어떻게 확인하는지(성공 기준)"를 명시한다.
- 단계 간 의존성이 있으면 순서를 명시하고, 없으면 병렬로 진행 가능하다고 표시한다.
- 프로젝트 고유 컨벤션(자원 키 규칙, 상태 갱신 순서, 알려진 안티패턴 등)이 문서화되어 있다면 체크리스트로 포함시킨다.

계획을 사용자에게 확인받은 후 실제 코드를 작성한다. 과도한 엔지니어링(불필요한 추상화, 안 쓰는 옵션/플래그, 발생하지 않을 상황에 대한 방어 코드)을 피한다.

문서에는 구현 계획 + 실제 구현 요약(파일별 변경 내용)을 기록한다.

**체크포인트**: 구현 완료 후 "테스트 단계로 진행할까요?"

## Phase 3 — 테스트 (`03-test.md`)

`02-implementation.md`를 다시 읽고 진행한다. Phase 2에서 이미 구현이 끝난 경우가 많으므로, **레드-그린을 형식적으로 가장하지 않는다.** 실제 목표는 결함 발견과 회귀 방지다.

1. 정상 / 엣지 / 에러 케이스 시나리오 목록을 먼저 작성한다.
2. 시나리오 기반으로 테스트를 작성한다. (Phase 2에서 테스트를 먼저 작성한 부분이 있으면 그 결과를 재검증하고, 여기서 처음 작성하는 테스트는 결함 발견 목적으로 쓴다.)
3. **검증은 프로젝트에 정의된 스크립트 범위에서** 다음 순서로 실행한다 — 변경 관련 테스트 → 타입 검사 → 린트 → 전체 테스트 → (필요 시) 프로덕션 빌드 → 기능별 수동 검증. 프로젝트에 없는 명령어를 임의로 만들지 않는다.

**테스트 실패·실행불가를 절대 숨기지 않는다.** 다음을 문서에 그대로 기록한다:
- 실패한 명령어와 실패한 테스트/검사 항목
- 이번 변경으로 생긴 실패인지, 원래부터 실패하던(무관한) 것인지 구분
- 수정 시도와 결과
- 실행하지 못한 검증 항목과 그 이유(환경/외부 API/Docker 등)

사용자 승인 없이 미완·미해결 상태를 "통과"로 간주하지 않는다.

**체크포인트**: 검증 결과(실패·미실행 포함)를 사용자에게 보고한 후 "결과 정리 단계로 진행할까요?"

## Phase 4 — 결과 (`04-result.md`)

1. 1~3단계에 걸친 전체 변경 diff를 리뷰한다 (가능하면 코드 리뷰 서브에이전트 활용).
2. 아래 형식으로 정리한다:

```markdown
## 결과 – {기능명} ({오늘 날짜})

### 잘된 점
-

### 발견된 이슈 / 기술부채
-

### 다음 리팩토링 포인트
-

### 배운 점
-
```

3. 마지막에 사용자에게 묻는다: "이 중 기억해둘 만한 피드백/프로젝트 정보가 있으면 메모리에 저장할까요?" — 승인 시에만 관련 memory 파일을 작성한다 (자동 저장 금지).

## 공통 규칙

- 각 단계의 산출물을 사용자에게 제시한 뒤 명시적 승인을 받아야 다음 단계로 진행한다. 수정 요청은 현재 단계에 반영하고 다시 승인을 받는다.
- 각 단계 시작 시 이전 단계 문서를 다시 읽어 컨텍스트를 유지한다.
- **변경 범위 통제**: 승인된 설계와 직접 관련된 범위만 수정한다. 계획에 없던 대규모 리팩터링, 의존성 추가·업그레이드, 공개 API 변경, 무관한 파일의 포맷 변경이 필요해지면 구현을 멈추고 사용자에게 알린 뒤 진행한다.
- 프로젝트에 `CLAUDE.md`/`docs`가 없으면 일반적인 관례를 기본값으로 사용한다.
- 사용자가 특정 단계를 건너뛰라고 명시적으로 요청하면 해당 문서 작성은 생략할 수 있으나, 건너뛴 사실을 다음 단계 문서에 기록한다.
- 한국어로 작성한다.
